# Тестирование брокеров сообщений (Message Brokers) — Kafka, RabbitMQ и др.

Раз у тебя в стеке Kafka — эта тема почти наверняка всплывёт на собеседовании, разберём детально.

## Зачем вообще тестировать брокер сообщений

Брокер — это асинхронная прослойка между сервисами, и баги здесь часто не видны в UI, а проявляются как "данные потерялись", "пришли дважды", "пришли не в том порядке" — сложно воспроизводимые проблемы, которые требуют отдельного подхода к тестированию.

## 1. Функциональное тестирование

### Producer (отправитель)

- Сообщение действительно отправляется в правильный **topic** (Kafka) / **queue/exchange** (RabbitMQ)
- Корректность **сериализации** payload (JSON, Avro, Protobuf)
- Корректность **key** сообщения (в Kafka key влияет на партиционирование — важно для проверки, что связанные сообщения попадают в одну партицию и сохраняют порядок)
- Проверка **headers/metadata** сообщения

### Consumer (получатель)

- Сообщение реально доходит и корректно десериализуется
- Обработка сообщения приводит к ожидаемому результату (запись в БД, вызов другого сервиса и т.д.)
- **Idempotency** — что будет, если одно и то же сообщение обработается дважды (при retry/redelivery) — не должно быть дублирования данных

### Порядок сообщений (Ordering)

- В Kafka порядок гарантирован **только внутри одной партиции** — если два сообщения с одним key, они попадут в одну партицию и сохранят порядок; с разными key — порядок между ними не гарантирован
- Частый вопрос: _"Как ты протестируешь, что порядок сохраняется?"_ → отправить серию сообщений с одинаковым key, проверить, что consumer получил их в том же порядке

### Delivery guarantees — критичная тема для собеседования

|Гарантия|Что значит|Риск|
|---|---|---|
|**At most once**|Сообщение доставится максимум 1 раз|Может потеряться|
|**At least once**|Сообщение доставится минимум 1 раз|Может задублироваться|
|**Exactly once**|Сообщение доставится ровно 1 раз|Сложнее всего реализовать, есть оверхед|

Нужно понимать, какая гарантия настроена в системе, и **целенаправленно тестировать её границы** — например, для "at least once" специально проверить, что consumer корректно обрабатывает дубликаты (идемпотентность на стороне бизнес-логики).

## 2. Нефункциональное тестирование (вспомним первую тему разговора)

### Performance / Load Testing

- **Throughput** — сколько сообщений в секунду брокер может обработать
- **Latency** — задержка от отправки producer'ом до получения consumer'ом (end-to-end latency)
- Инструменты: **kafka-producer-perf-test** / **kafka-consumer-perf-test** (встроенные CLI-утилиты Kafka), **JMeter** с плагином для Kafka, **Gatling**

### Consumer Lag (специфично для Kafka)

```
Lag = Offset последнего сообщения в партиции − Offset, который прочитал consumer
```

Показывает, насколько consumer "отстаёт" от producer'а. Тестируется через `kafka-consumer-groups.sh --describe`. Растущий lag — сигнал, что consumer не успевает обрабатывать поток (нужно больше consumer'ов в группе или оптимизация обработки).

### Отказоустойчивость (Resilience/Chaos Testing)

- Что будет при падении **брокера** (одного узла из кластера) — данные не теряются, если репликация настроена корректно (`replication.factor`)
- Что будет при падении **consumer'а** посреди обработки — сообщение не должно "потеряться" (проверка `offset commit` стратегии — commit до или после обработки)
- Restart producer/consumer — переподключение, ретраи

### Тестирование retry и Dead Letter Queue (DLQ)

- Если сообщение не удалось обработать (например, ошибка в бизнес-логике) — уходит ли оно в DLQ после N попыток
- Проверка, что "плохие" сообщения не блокируют весь поток обработки остальных сообщений

## 3. Как тестировать на практике — инструменты

### Ручное/exploratory тестирование

- **Kafka CLI**: `kafka-console-producer.sh` / `kafka-console-consumer.sh` — быстро отправить/прочитать сообщение вручную
- **Kafka UI / AKHQ / Conduktor / Redpanda Console** — GUI для просмотра топиков, партиций, сообщений, consumer groups — аналог DevTools, но для Kafka
- **RabbitMQ Management UI** — встроенная веб-панель для queues/exchanges

### Automation-тестирование (актуально для твоей роли)

**Testcontainers** — ключевой инструмент, стоит знать детально:

```java
@Testcontainers
class KafkaIntegrationTest {
    @Container
    static KafkaContainer kafka = new KafkaContainer(
        DockerImageName.parse("confluentinc/cp-kafka:7.5.0")
    );

    @Test
    void testProducerConsumer() {
        // поднимается реальный Kafka в Docker для теста
        // отправляем сообщение, проверяем, что consumer его получил
    }
}
```

Позволяет поднять **реальный** брокер в Docker-контейнере для интеграционных тестов, не завися от внешней тестовой инфраструктуры — тест воспроизводим и изолирован.

**Spring Kafka Test** (раз у тебя Spring в стеке):

```java
@EmbeddedKafka(partitions = 1, topics = {"test-topic"})
class KafkaListenerTest {
    // встроенный in-memory Kafka для тестов, без Docker
}
```

**Awaitility** — для проверки асинхронных сценариев (сообщение обработается не мгновенно):

```java
await().atMost(10, SECONDS)
       .untilAsserted(() -> 
           assertThat(consumerRecords).hasSize(1)
       );
```

Важный момент: **нельзя** просто написать `assertEquals` сразу после отправки — обработка асинхронна, нужно ждать с таймаутом.

## 4. Специфичные для Kafka сценарии тестирования (раз это твой стек)

- **Партиционирование** — сообщения с одинаковым key всегда попадают в одну и ту же партицию (можно проверить через `Partitioner` логику)
- **Rebalancing** — что происходит при добавлении/удалении consumer'а в consumer group (перераспределение партиций) — проверка, что во время rebalance не теряются и не дублируются сообщения сверх ожидаемого
- **Retention policy** — сообщения удаляются из топика через настроенное время/объём — тест, что consumer, который "отстал" дольше retention period, теряет доступ к старым сообщениям (`OffsetOutOfRangeException`)
- **Schema Registry / Avro compatibility** — если используется Avro, тестирование обратной/прямой совместимости схем при эволюции формата сообщений (backward/forward compatibility)

## Частые вопросы на собеседовании

**"Как протестировать, что consumer корректно обрабатывает дубликаты?"** → Отправить одно и то же сообщение (с одинаковым уникальным ID/ключом в payload) дважды, проверить, что в результате обработки нет дублирования данных (например, запись в БД не задвоилась) — это проверка идемпотентности на уровне бизнес-логики, а не самого брокера.

**"Как ты протестируешь, что при падении consumer'а сообщение не теряется?"** → Убить процесс consumer'а до commit offset, поднять заново, проверить, что необработанное сообщение прочиталось повторно (поведение зависит от стратегии commit — manual vs auto commit).

**"В чём разница между тестированием очереди (RabbitMQ) и топика (Kafka)?"** → В RabbitMQ сообщение обычно удаляется из очереди после успешной обработки (point-to-point), в Kafka сообщение остаётся в топике до истечения retention period и может быть прочитано несколькими независимыми consumer group одновременно (pub-sub с "перечитыванием" истории) — это принципиально разные модели, и тестовые сценарии тоже разные.

**"Как проверить производительность Kafka под нагрузкой без реального продакшн-трафика?"** → `kafka-producer-perf-test.sh` для генерации синтетической нагрузки, замер throughput/latency, сравнение с baseline-метриками.
