# Тестирование Redis (кэша) — для QA собеседования

Продолжаем по твоему стеку — раз Redis используется как кэш, разберём, что именно нужно тестировать и какие вопросы могут спросить.

## Зачем вообще тестировать кэш

Кэш — это "оптимизация поверх истины" (истина в PostgreSQL, кэш — её быстрая копия). Главный риск — **рассинхронизация**: кэш показывает устаревшие данные, пока в основной БД уже всё изменилось. Большинство тестовых сценариев вращаются именно вокруг этого.

## 1. Функциональное тестирование — базовые сценарии

### Cache Hit / Cache Miss

- **Cache Hit** — данные есть в Redis, запрос идёт в кэш, не трогая БД (проверяется через логи/метрики — запрос к БД не должен произойти)
- **Cache Miss** — данных в кэше нет, запрос идёт в БД, результат кладётся в кэш (**cache population**)

Практическая проверка: замерить время ответа — cache hit должен быть значительно быстрее cache miss (это же тестируется и как перфоманс-метрика).

### TTL (Time To Live) — истечение срока жизни

```java
redisTemplate.opsForValue().set("user:123", userData, Duration.ofMinutes(10));
```

- Проверка, что данные реально удаляются из кэша после истечения TTL
- Проверка **граничных условий** (вспомним boundary value analysis из первой темы) — что происходит точно в момент истечения TTL, за секунду до, через секунду после
- Проверка, что после истечения TTL следующий запрос идёт в БД (cache miss) и кэш заново заполняется

### Cache Invalidation (инвалидация кэша) — самая частая тема на собеседовании

Ключевой вопрос: **что происходит с кэшем, когда данные в БД меняются?**

Сценарии для тестирования:

- Обновление записи (`UPDATE` в БД) → кэш должен либо обновиться, либо инвалидироваться (удалиться), чтобы следующий запрос взял свежие данные
- Удаление записи (`DELETE` в БД) → соответствующий ключ должен быть удалён из Redis
- Проверка **stale data** (устаревших данных) — если инвалидация не сработала, пользователь увидит старые данные, это баг

### Основные стратегии инвалидации (нужно уметь объяснить разницу)

|Стратегия|Как работает|Что тестировать|
|---|---|---|
|**TTL-based**|Данные просто "протухают" по времени|Проверка точного времени истечения, поведение при частых обновлениях данных внутри TTL-окна|
|**Write-through**|При записи в БД сразу обновляется и кэш|Синхронность — кэш и БД никогда не расходятся, но чуть медленнее запись|
|**Write-behind (write-back)**|Запись сначала в кэш, потом асинхронно в БД|Риск потери данных при падении системы до синхронизации — важный тест-кейс|
|**Cache-aside (lazy loading)**|Приложение само проверяет кэш, при miss — читает БД и кладёт в кэш|Самая частая схема на практике — тестировать race condition при одновременном miss от нескольких потоков|
|**Explicit invalidation**|При изменении данных явно вызывается `DEL`/`EXPIRE` для ключа|Проверка, что разработчик не забыл инвалидировать **все** связанные ключи (частый баг — обновили одну запись, а закэшированный список с ней не тронули)|

## 2. Race Conditions — сложная, но частая тема для более сильных кандидатов

### Cache Stampede (thundering herd problem)

Ситуация: TTL истёк, и **множество запросов одновременно** видят cache miss → все одновременно бьют в БД, вместо того чтобы один запрос обновил кэш, а остальные подождали.

**Как тестировать**: сгенерировать конкурентную нагрузку (например, JMeter/Gatling) точно в момент истечения TTL, проверить количество реальных запросов к БД — в идеале должен быть один, а не N (если реализована защита типа distributed lock или `SETNX`).

### Race condition при одновременной записи и чтении

- Поток A обновляет запись в БД и инвалидирует кэш
- Поток B в этот же момент читает "старые" данные и кладёт их обратно в кэш (после того, как поток A уже удалил)
- Результат: в кэше опять оказываются устаревшие данные, несмотря на то что инвалидация была вызвана

Это классический сложный баг, который стоит уметь описать на собеседовании как пример понимания consistency-проблем.

## 3. Нефункциональное тестирование Redis

### Eviction Policy (вытеснение при переполнении памяти)

Redis настраивается на разные политики вытеснения при достижении `maxmemory`:

- `noeviction` — новые записи не принимаются, ошибка
- `allkeys-lru` — вытесняются наименее недавно использованные ключи (Least Recently Used)
- `allkeys-lfu` — вытесняются наименее часто используемые (Least Frequently Used)
- `volatile-ttl` — вытесняются ключи с истекающим TTL в первую очередь

**Тест-кейс**: забить Redis данными до предела памяти, проверить, что вытеснение работает согласно настроенной политике, и приложение корректно обрабатывает cache miss для вытесненных ключей (не должно падать).

### Persistence (сохранность данных при рестарте)

Redis поддерживает **RDB** (снепшоты) и **AOF** (append-only log). Тестовый сценарий: перезапустить Redis, проверить, восстановились ли данные согласно настроенной persistence-стратегии — важно понимать, что кэш **не обязан** быть персистентным (это его нормальное поведение), но если бизнес-логика этого ожидает — нужно тестировать отдельно.

### Failover / High Availability

- Redis Sentinel / Redis Cluster — тестирование поведения приложения при падении master-узла (происходит ли переключение на replica без потери доступности)
- Проверка, что приложение gracefully деградирует, если Redis вообще недоступен (fallback на прямой запрос к БД, а не полный отказ сервиса) — это отдельный важный нефункциональный сценарий: **"что будет, если кэш упал целиком"**

### Performance

- Latency отдельных операций (`GET`/`SET`) — обычно суб-миллисекундные, замеры через `redis-cli --latency`
- Throughput под нагрузкой — `redis-benchmark` (встроенная утилита)

## 4. Инструменты для тестирования

### Ручное/exploratory

- **redis-cli** — прямой доступ к консоли Redis

```bash
redis-cli GET user:123
redis-cli TTL user:123        # сколько секунд осталось до истечения
redis-cli KEYS "user:*"       # поиск ключей по паттерну (осторожно, не для прода — блокирующая операция)
redis-cli MONITOR             # live-просмотр всех команд в реальном времени — аналог Network tab, но для Redis
```

- **RedisInsight** — официальный GUI-клиент от Redis Labs, визуализация ключей, memory usage, TTL

### Automation (Java-стек)

**Testcontainers** (та же логика, что и с Kafka):

```java
@Testcontainers
class RedisCacheTest {
    @Container
    static GenericContainer<?> redis = new GenericContainer<>("redis:7.2")
        .withExposedPorts(6379);

    @Test
    void testCacheInvalidationOnUpdate() {
        // 1. Populate cache
        // 2. Update entity in DB
        // 3. Assert cache key is invalidated/updated
    }
}
```

**Тестирование через Spring** (если кэш реализован через `@Cacheable`/`@CacheEvict`):

```java
@Cacheable(value = "users", key = "#id")
public User getUser(Long id) { ... }

@CacheEvict(value = "users", key = "#id")
public void updateUser(Long id, User user) { ... }
```

Тестовый сценарий: вызвать `getUser` (кэшируется) → вызвать `updateUser` → снова вызвать `getUser` → проверить, что метод сходил в "БД" повторно (через Mockito `verify(repository, times(2))`), а не взял устаревшие данные из кэша.

## Частые вопросы на собеседовании

**"Как ты протестируешь, что кэш действительно используется, а не каждый раз идёт запрос в БД?"** → Мокировать/спайить репозиторий (Mockito `verify(times(1))`), либо смотреть логи SQL-запросов (Hibernate `show-sql`), либо замерить время ответа (cache hit заметно быстрее).

**"Приложение показывает устаревшие данные после обновления — как будешь искать причину?"** → Проверить: 1) вызывается ли инвалидация кэша в коде обновления вообще, 2) не race condition ли это (проверить логи по времени — что было раньше, инвалидация или повторное чтение), 3) TTL — может, обновление сработало, но старый TTL ещё не истёк, если инвалидация не explicit.

**"Что будет с приложением, если Redis полностью упадёт?"** → Хороший ответ показывает понимание отказоустойчивости — приложение должно **деградировать gracefully**: fallback на прямые запросы к БД (медленнее, но работает), а не падать целиком. Это стоит явно протестировать как отдельный нефункциональный сценарий (Resilience Testing).

**"Как воспроизвести Cache Stampede в тестах?"** → Конкурентная нагрузка (JMeter thread group с одновременным стартом) точно в момент истечения TTL ключа, замер количества запросов, реально дошедших до БД.
