# Виды хранилищ в браузере — для QA собеседования

Тема логично продолжает разговор про DevTools → Application tab, где мы это уже упоминали вскользь. Разберём подробно.

## Сравнительная таблица (основа для собеседования)

| Хранилище          | Объём            | Срок жизни                    | Доступность        | Отправка на сервер         |
| ------------------ | ---------------- | ----------------------------- | ------------------ | -------------------------- |
| **Cookies**        | ~4 KB            | Настраиваемый (expiration)    | Клиент + сервер    | Да, с каждым HTTP-запросом |
| **LocalStorage**   | ~5-10 MB         | Пока не удалят вручную        | Только клиент (JS) | Нет                        |
| **SessionStorage** | ~5-10 MB         | До закрытия вкладки           | Только клиент (JS) | Нет                        |
| **IndexedDB**      | Сотни MB / GB    | Пока не удалят вручную        | Только клиент (JS) | Нет                        |
| **Cache Storage**  | Зависит от диска | Управляется Service Worker'ом | Только клиент      | Нет                        |

## 1. Cookies

Самое старое хранилище, единственное, которое **автоматически отправляется на сервер** с каждым запросом (в заголовке `Cookie`).

### Ключевые атрибуты (частый вопрос на собеседовании)

```
Set-Cookie: sessionId=abc123; Expires=Wed, 09 Jun 2027 10:18:14 GMT; 
            Secure; HttpOnly; SameSite=Strict; Path=/
```

- **`Expires` / `Max-Age`** — время жизни; если не задано — cookie удалится при закрытии браузера (**session cookie**)
- **`Secure`** — cookie передаётся только по HTTPS
- **`HttpOnly`** — cookie недоступен через JavaScript (`document.cookie` его не увидит) — защита от XSS-атак, важно для security-тестирования
- **`SameSite`** (`Strict`/`Lax`/`None`) — контролирует, отправляется ли cookie при кросс-доменных запросах — защита от CSRF-атак

### Зачем QA это знать

- Тестирование сессий/авторизации ("запомнить меня", истечение сессии)
- Security-тестирование: проверка, что токен авторизации имеет `HttpOnly` и `Secure` (иначе уязвимость — токен можно украсть через XSS)
- Тестирование consent-баннеров (GDPR) — cookie для хранения согласия пользователя

## 2. LocalStorage

Хранилище **ключ-значение** (только строки), данные сохраняются **навсегда**, пока пользователь/скрипт их не удалит явно (не зависит от закрытия браузера).

```javascript
localStorage.setItem('theme', 'dark');
localStorage.getItem('theme');   // 'dark'
localStorage.removeItem('theme');
localStorage.clear();
```

### Особенности

- Данные **не отправляются на сервер** автоматически — только клиентское хранение
- **Доступ в пределах одного origin** (протокол + домен + порт) — важно: `http://site.com` и `https://site.com` — это разные origin с разным LocalStorage
- Синхронный API — может блокировать основной поток при больших объёмах данных (в отличие от IndexedDB)

### Зачем QA это знать

- Тестирование пользовательских настроек (тема, язык интерфейса, состояние сайдбара)
- Часто там хранят JWT-токены (хотя это спорная практика с точки зрения security — LocalStorage доступен через JS, значит уязвим к XSS, в отличие от `HttpOnly` cookie)
- Проверка edge case: что будет, если очистить LocalStorage вручную во время работы приложения (баг-репорты часто требуют такой сценарий)

## 3. SessionStorage

Функционально идентичен LocalStorage (тот же API), но **данные живут только пока открыта вкладка** — при закрытии вкладки/браузера данные удаляются.

```javascript
sessionStorage.setItem('formDraft', JSON.stringify(formData));
```

### Ключевое отличие от LocalStorage

- **Изолирован per-tab** — если открыть два таба одного сайта, у каждого будет **своё** SessionStorage (в отличие от LocalStorage, который общий для всех вкладок одного origin)

### Зачем QA это знать

- Тестирование многошаговых форм (сохранение черновика между шагами, но не между сессиями)
- Проверка поведения при открытии нескольких вкладок одновременно — частый edge case в тест-кейсах

## 4. IndexedDB

Полноценная **NoSQL база данных внутри браузера** — для структурированных данных большого объёма, с индексами и транзакциями.

### Ключевые отличия

- **Асинхронный API** (не блокирует UI, в отличие от LocalStorage)
- Хранит не только строки — объекты, файлы, blob'ы
- Используется для offline-first приложений, PWA (кэширование данных для работы без интернета)

### Зачем QA это знать

- Актуально при тестировании PWA (Progressive Web Apps) — offline-режим, синхронизация данных при восстановлении соединения
- Более сложный для дебага — нужно смотреть DevTools → Application → IndexedDB, там видно таблицы/объекты

## 5. Cache Storage (Service Worker Cache)

Используется **Service Worker'ами** для кэширования сетевых запросов (файлы, API-ответы) — основа offline-режима в PWA.

### Зачем QA это знать

- Тестирование, что приложение действительно работает offline (что реально закэшировано)
- Проверка обновления кэша при выходе новой версии приложения (частый баг: пользователь видит старую версию сайта из-за агрессивного кэша)

## Как всё это смотреть в DevTools

Application tab → в левом меню:

- **Storage** → Cookies, Local Storage, Session Storage, IndexedDB, Cache Storage — всё в одном месте, можно вручную добавлять/удалять/редактировать записи для тестирования edge cases

## Частые вопросы на собеседовании

**"В чём разница между Cookies и LocalStorage?"** → Главное отличие: Cookies автоматически отправляются на сервер с каждым запросом (и имеют ограничение ~4KB), LocalStorage — чисто клиентское хранилище большего объёма, сервер о нём ничего не знает, пока JS явно не отправит данные.

**"Где лучше хранить JWT-токен — Cookie или LocalStorage?"** → Хороший ответ: `HttpOnly` + `Secure` Cookie считается более безопасным, потому что недоступен через JavaScript (защита от XSS). LocalStorage удобнее в разработке, но уязвим, если на сайте есть XSS-уязвимость — это частый вопрос на стыке QA и security testing.

**"Как протестировать, что данные корректно очищаются при логауте?"** → Проверить, что после logout очищены: cookie сессии, LocalStorage (если там токен/пользовательские данные), SessionStorage — через DevTools Application tab до и после действия.

**"Приложение падает при заполненном LocalStorage — как воспроизвести?"** → QuotaExceededError — можно вручную забить LocalStorage большим объёмом данных через консоль DevTools, чтобы проверить, как приложение обрабатывает превышение лимита (~5-10 MB).
