# Метрики в QA — для собеседования

## Зачем это спрашивают

Метрики показывают, умеешь ли ты не просто "тестировать", а измерять эффективность процесса тестирования и аргументированно доносить результаты до менеджмента. Частая тема для более осознанных кандидатов (не джуновский уровень "просто пиши баг-репорты").

## 1. Метрики покрытия (Coverage Metrics)

### **Test Coverage** (покрытие требований тестами)

```
Test Coverage = (Кол-во требований, покрытых тестами / Общее кол-во требований) × 100%
```

Показывает, насколько полно тест-кейсы покрывают функциональные требования.

### **Code Coverage** (покрытие кода)

```
Code Coverage = (Кол-во строк кода, выполненных тестами / Общее кол-во строк) × 100%
```

Обычно измеряется инструментами типа JaCoCo (для Java), считается разработчиками/automation QA. Виды:

- **Line coverage** — покрытие строк
- **Branch coverage** — покрытие условных веток (if/else)
- **Function coverage** — покрытие вызванных функций

Важный нюанс на собеседовании: **высокий code coverage не гарантирует отсутствие багов** — можно "выполнить" строку кода тестом без проверки реального результата (assert). Это частая ловушка вопроса.

### **Requirement Traceability**

Связь между требованиями → тест-кейсами → багами — обычно через Requirement Traceability Matrix (RTM), показывает "непокрытые" требования.

## 2. Метрики дефектов (Defect Metrics)

### **Defect Density (плотность дефектов)**

```
Defect Density = Кол-во найденных дефектов / Размер модуля (KLOC или story points)
```

Помогает понять, какие модули наиболее проблемные — куда направить больше тестирования.

### **Defect Leakage (утечка дефектов)**

```
Defect Leakage = (Баги, найденные на проде / Общее кол-во багов) × 100%
```

Ключевая метрика эффективности тестирования — показывает, сколько багов "проскочило" мимо QA на продакшн. Чем ниже — тем лучше работает процесс тестирования.

### **Defect Rejection Ratio (процент отклонённых багов)**

```
DRR = (Кол-во отклонённых багов / Общее кол-во заведённых багов) × 100%
```

Высокий процент может говорить о том, что QA плохо разбирается в системе или пишет некачественные баг-репорты (например, не может воспроизвести, или это "not a bug" — фича так задумана).

### **Defect Removal Efficiency (DRE)**

```
DRE = (Баги, найденные до релиза / (Баги до релиза + Баги после релиза)) × 100%
```

Один из важнейших показателей качества тестового процесса — насколько эффективно QA "отлавливает" баги до выхода на прод.

### **Defect Age / Defect Resolution Time**

Среднее время от момента заведения бага до его фикса — показывает скорость реакции команды разработки.

### **Bugs by Severity/Priority distribution**

Распределение багов по критичности (Blocker/Critical/Major/Minor) — помогает понять реальное качество релиза (100 minor-багов менее критично, чем 1 blocker).

## 3. Метрики выполнения тестов (Test Execution Metrics)

### **Test Case Execution Rate**

```
= (Выполненные тест-кейсы / Запланированные тест-кейсы) × 100%
```

Насколько план тестирования реально выполнен к моменту релиза.

### **Test Pass Rate / Pass Percentage**

```
= (Пройденные тесты / Всего выполненных тестов) × 100%
```

### **Test Case Effectiveness**

```
= (Кол-во багов, найденных через тест-кейсы / Общее кол-во найденных багов) × 100%
```

Показывает, насколько тест-кейсы вообще полезны в нахождении багов (в сравнении с exploratory testing, например).

## 4. Метрики автоматизации (Automation Metrics) — важно для твоего профиля

### **Automation Coverage**

```
= (Автоматизированные тест-кейсы / Тест-кейсы, пригодные для автоматизации) × 100%
```

Важный нюанс: считается не от **всех** тест-кейсов, а от тех, которые **имеет смысл** автоматизировать (не все UI-кейсы стоит автоматизировать, например одноразовые exploratory-сценарии).

### **Test Execution Time (до/после автоматизации)**

Сравнение времени ручного прогона регресса vs автоматизированного — классический аргумент в пользу ROI автоматизации.

### **Flakiness Rate (частота нестабильных тестов)**

```
= (Кол-во flaky-прогонов / Общее кол-во прогонов теста) × 100%
```

Критически важная метрика для Automation QA — высокий процент flaky-тестов подрывает доверие к CI-пайплайну (команда начинает игнорировать красные тесты).

### **Automation ROI (Return on Investment)**

Оценка, окупились ли вложенные в автоматизацию усилия — сравнение стоимости написания/поддержки автотестов vs экономии времени на ручном регрессе.

### **Mean Time to Detect / Mean Time to Repair (MTTD / MTTR)**

Особенно актуально при CI/CD — как быстро пайплайн обнаруживает баг после коммита (MTTD) и как быстро команда его фиксит (MTTR).

## 5. Метрики процесса/эффективности (Process Metrics)

### **Test Efficiency**

```
= Кол-во найденных дефектов / Затраченное время на тестирование
```

### **Cost of Quality**

Соотношение затрат на предотвращение багов (review, тестирование) vs затрат на исправление багов, найденных поздно (на проде исправление стоит на порядки дороже — классическая иллюстрация "shift-left" подхода).

### **Requirement Volatility**

Как часто меняются требования во время цикла тестирования — влияет на переработку тест-кейсов.

## Частые вопросы на собеседовании

**"Какая метрика самая важная для QA?"** Хороший ответ: нет одной "самой важной" — зависит от цели. Для оценки качества релиза — Defect Leakage/DRE, для эффективности автоматизации — Automation Coverage + Flakiness Rate, для планирования — Test Execution Rate.

**"Высокий Code Coverage (95%) — значит ли это, что продукт качественный?"** Ловушка вопроса — нет. Coverage показывает, что код **выполнялся** во время теста, но не гарантирует, что там были правильные assertions. Можно иметь 100% coverage и пропустить критичный баг, если тест не проверяет нужное условие.

**"Как ты будешь измерять эффективность внедрения автоматизации в команде?"** Хороший ответ: сравнить Automation Coverage до/после, Test Execution Time (сколько раньше занимал ручной регресс vs сейчас), Defect Leakage (стало ли меньше багов на проде), Flakiness Rate (насколько стабильны автотесты).

**"Что такое flaky-тест и почему это плохая метрика для CI?"** Тест, который иногда падает, иногда проходит без изменений в коде — обычно из-за race conditions, неявных ожиданий, зависимости от внешних сервисов. Подрывает доверие к пайплайну — команда начинает игнорировать красные билды ("а, это опять флак"), что маскирует реальные баги.
