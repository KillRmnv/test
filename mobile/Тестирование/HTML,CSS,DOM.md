# HTML, DOM, CSS — подробно для QA (Manual & Automation) собеседования

## 1. HTML — основы, которые должен знать QA

### Структура документа

```html
<!DOCTYPE html>
<html>
  <head>...</head>
  <body>...</body>
</html>
```

### Ключевые атрибуты для тестировщика

- **`id`** — уникальный идентификатор элемента (лучший локатор для автотестов — быстрый и однозначный)
- **`class`** — может быть у нескольких элементов, часто используется и для стилей, и для локаторов
- **`name`** — часто используется в формах, важен для тестирования отправки данных
- **`data-*`** (data-testid, data-qa, data-cy) — специально добавляемые атрибуты для тестирования, не завязанные на стили/логику. **Это лучшая практика** — если на проекте есть `data-testid`, использовать его вместо `class`/`xpath`, потому что дизайнеры могут менять классы, а тестовые атрибуты — нет.
- **`aria-*`** — атрибуты доступности (accessibility), тоже часто используются как локаторы (особенно в Playwright — `getByRole`)

### Семантические теги (важно для accessibility-тестирования)

`<header>`, `<nav>`, `<main>`, `<footer>`, `<section>`, `<article>`, `<button>` vs `<div onclick="">` — семантическая верстка важна и для SEO, и для screen reader'ов, и для стабильности локаторов.

### Формы

`<form>`, `<input type="text/checkbox/radio/email">`, `<select>`, `<textarea>` — частая область функционального тестирования (валидация полей, required, maxlength, pattern).

## 2. DOM (Document Object Model)

### Что это

DOM — это **объектное представление HTML-документа в памяти браузера**, дерево узлов (nodes), с которым можно взаимодействовать через JavaScript.

Ключевая мысль для собеседования: **HTML — это статичная разметка (то, что пришло с сервера), а DOM — это живая, динамическая структура в браузере**, которая может отличаться от исходного HTML после выполнения JS (например, React/Vue-приложения рендерят DOM динамически, и "View Page Source" покажет пустой `<div id="root">`, а реальный DOM в DevTools — полное дерево).

### Почему это критично для автоматизации

- Selenium/Playwright/Cypress работают именно с **DOM**, а не с исходным HTML-файлом
- Если элемент появляется динамически (AJAX, SPA-фреймворк) — нужны **явные ожидания (explicit waits)**, потому что DOM ещё не готов в момент попытки найти элемент
- **Shadow DOM** — отдельная тема: инкапсулированное поддерево DOM (используется в Web Components), обычные локаторы его не видят, нужны специальные методы (`shadowRoot` в Playwright/Selenium)

### DOM Tree и навигация

- Parent/Child/Sibling — отношения между узлами, важно при написании XPath (`//div[@class='x']/following-sibling::span`)
- DOM события: `click`, `change`, `submit`, `load` — понимание, что синтетический клик через JS (`element.click()` в консоли) может не триггерить те же события, что реальный клик пользователя — частая причина "тест проходит, а руками баг воспроизводится" и наоборот

## 3. CSS — что важно для QA

### CSS-селекторы (критично для локаторов в автотестах)

|Селектор|Пример|Что означает|
|---|---|---|
|По id|`#login-btn`|элемент с id="login-btn"|
|По классу|`.error-message`|элемент с class="error-message"|
|По тегу|`input`|все input-элементы|
|Потомок|`form input`|input внутри form (любой вложенности)|
|Прямой потомок|`form > input`|input — прямой child form|
|Атрибут|`input[type="email"]`|input с атрибутом type=email|
|Псевдоклассы|`li:nth-child(2)`, `input:disabled`, `a:hover`|состояние/позиция элемента|
|Комбинация|`.form-group > input[type="text"]:not(.hidden)`|сложный составной селектор|

### CSS Selector vs XPath — частый вопрос на собеседовании

||CSS Selector|XPath|
|---|---|---|
|Скорость|Быстрее|Медленнее|
|Навигация вверх по дереву|Нельзя (родитель)|Можно (`../parent::div`)|
|Поиск по тексту|Нельзя напрямую|Можно (`//button[text()='Submit']`)|
|Читаемость|Проще|Сложнее, но гибче|
|Поддержка в браузерах|Нативная (querySelector)|Через движок XPath|

Хороший ответ на собеседовании: _"Я предпочитаю CSS-селекторы за скорость и простоту, но использую XPath, когда нужен поиск по тексту или навигация к родительскому элементу, которую CSS не поддерживает."_

### CSS-специфичность (specificity) — может спросить, если баг в стилях

Порядок приоритета (от низкого к высокому): `тег` < `класс/атрибут/псевдокласс` < `id` < `!important`

Полезно, когда нужно понять, почему применился не тот стиль (например, баг "кнопка не того цвета").

### Что важно для UI-тестирования

- **Box model**: content → padding → border → margin — часто источник визуальных багов (элемент "не помещается", "наезжает")
- **Display**: `block`, `inline`, `inline-block`, `flex`, `grid`, `none` (важно отличать `display: none` от `visibility: hidden` — первое элемент реально исчезает из layout и его нельзя кликнуть, второе — элемент невидим, но занимает место)
- **Position**: `static`, `relative`, `absolute`, `fixed`, `sticky` — важно при тестировании оверлеев, модалок, sticky-хедеров
- **z-index** — частая причина бага "элемент не кликается", потому что другой элемент перекрывает его сверху

### `visibility: hidden` vs `display: none` vs `opacity: 0` — частый вопрос

- `display: none` — элемент удалён из layout, не занимает место, не доступен в DOM для клика
- `visibility: hidden` — элемент невидим, но место в layout занимает
- `opacity: 0` — элемент технически видим и кликабелен (!), просто прозрачен — важно для security/UX тестирования (скрытые, но активные элементы — потенциальная уязвимость)

## Частые практические вопросы на собеседовании

- _"Элемент есть в DOM, но Selenium выдаёт ElementNotInteractableException — почему?"_ → элемент может быть `display: none`, скрыт другим элементом (z-index), находится за пределами viewport, или не завершилась анимация
- _"Как найти элемент, если у него нет id и class?"_ → через связь с соседними элементами (sibling/parent в XPath), через текст, через `nth-child`, либо попросить разработчиков добавить `data-testid`
- _"Что будет, если элемент в Shadow DOM?"_ → обычный `find_element` его не увидит, нужен отдельный подход через shadow root
